## A66
【北船#27】
了解しました。ここは数式的に正しいことと日本語として誤解しにくいことを同時に満たした方がよい箇所ですね。
先に結論、そのあと理由を書きます。

まず結論：仕様文のおすすめ表現（そのまま貼れる版）
推奨案（物理量が一貫する書き方）

ミックスは、右ボタンを押したままマウスを上方向にドラッグすることで「ポンプ」される。
ポンプ操作中、ドラッグ距離100ピクセルごとに円の半径を50%に縮小する。
ミックス量は円の面積に基づいて算出され、減少した面積分がミックス値として回収される。
回収されたミックス値は、時間経過により最終的にインスピへ変換される。

なぜこの書き方が良いか（重要）

元の文には、物理量が3回すり替わる地雷があります。

半径を操作している

面積で量を決めている

最終的に抽象値（ミックス / インスピ）になる

これを曖昧に書くと、後で必ず
「50%って半径？面積？毎フレーム？累積？」
という事故が起きます。なので、

操作量：ドラッグ距離（px）

見た目：半径（r）

量の正体：面積（πr²）

を文中で明確に分離しています。

数学的に正しい補足（仕様理解用）

「半径50%」という表現は、内部的にはこういう意味です。

半径：r → 0.5r

面積：A → 0.25A

失われた面積：75%

つまりポンプ1段階で

見た目は半分
中身はごっそり

という、かなり攻撃的な挙動です。
これは悪い意味ではなく、“ポンプ感”が強い設計です。

この性質を文章側で隠さないために
「半径」「面積」を両方明示しています。

もう少しゲーム寄りにした言い換え案（演出重視）

もし数式臭を弱めたいなら、これもアリです。

ミックスポップはポンプ操作によって圧縮される。
上方向へのドラッグ100ピクセルごとにポップは一段階圧縮され、
圧縮によって失われた内容量がミックスとして抽出される。
抽出されたミックスは、後段処理でインスピへと変換される。

※ただしこの場合、実装コメントには必ず「面積基準」と書くべきです。

逆に避けた方がいい表現（事故る）

「50%ずつ減る」
→ 何が50%か不明

「中身を変換する」
→ いつ、どれだけ、どう変換されるか不明

「縮小してミックスになる」
→ 見た目と量の関係が消える

まとめ（北船的に一言）

この箇所は
「半径を操作するUI」＋「面積で管理されるリソース」
という二重構造が肝です。

なので文章でも

操作対象（半径）

計算基準（面積）

リソース遷移（ミックス → インスピ）

を分けて書くのが正解です。
上の「推奨案」は、その最短ルートです。

## A64
Pre_Mix って、名前が「何が“Pre”なのか」分からなくて、未来の自分を雑に殴るタイプの変数名なんだよね。なので “それが何の状態の量なのか” を名前に入れるのが勝ち。

あなたの仕様だと、ミックスは 右ドラッグで消費されるリソース（円の面積で表現） で、さらに 最終的にインスピへ変換 される。だから Pre_Mix が指してる意味はだいたい次のどれか。

1) 「ミックスポップの残量」なら（UI/ゲージ）

mixCharge / MixCharge（いちばん無難。充填/消費の挙動と合う）

mixReserve（“予備タンク”感。補充仕様とも相性いい）

mixFill / mixFill01（0〜1正規化の残量ならこれが強い）

mixPopFill（“ミックスポップ”に紐づくことを明示したいなら）

2) 「インスピ変換待ちのミックス」なら（中間バッファ）

pendingMix（いちばん意図が伝わる）

mixToConvert（変換前であることが直球）

mixStaging / mixBuffer（工程の一時置き場）

3) 「円の面積/半径そのもの」を持ってるなら（物理量）

mixBubbleAreaPx2（面積で管理してるなら、これが誤解ゼロ）

mixBubbleRadiusPx（半径で持ってるなら）

（0〜1なら）mixBubbleFill01

俺のおすすめ（迷ったらこれ）

ゲージ残量なら：mixCharge（または 0〜1なら mixFill01）

変換待ちなら：pendingMix

Pre_ を捨てて、「何の」「どの状態」 を名前に入れる。これだけで半年後のあなたがキレなくて済む。
