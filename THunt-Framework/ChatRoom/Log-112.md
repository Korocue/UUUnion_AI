# Q113

## A113
(2) AppPlan.md に置くのが正解寄り。
Core（THunt-Framework/Core）をアプリごとに書き換えたくないなら、App側の一次情報（＝AppPlan）に “このリポジトリのAppRootはここ” を宣言して、Orchestratorはそれを読んで使うだけにするのが一番事故りません。

AppPlan.md：プロジェクト固有の前提（ターゲット、完成定義、リポジトリ都合）を置く場所。ここを単一の正本にする。

Orchestrator.md：毎回の実行手順の入口。AppPlanを参照して指示を組み立てるだけ（値の“正本”にはしない）。

Spec.md：ゲーム仕様の正本。パス設定みたいな運用インフラを混ぜると後で腐る。

置き方（提案フォーマット）

AppPlan.md の上のほうに、こういう “環境/配置” セクションを追加：

```
## 0. Repo / Path Settings（運用）
- AppRoot: Assets/THuntApp
- DevRoot: Assets/THuntApp/Dev
- EditableRoot: Assets/THuntApp      # Codex編集可の基準
- Protected: Assets/THuntApp/Dev     # 編集禁止
```

Orchestrator.md 側は「AppPlan.md の AppRoot を参照して、編集可能パスを決める」って書くだけ。
AGENTS.md 側は /App/ 固定表記を <AppRoot> に変えて、**“AppRoot の実値は AppPlan.md に定義される”**と1行足せば終わり。

つまり：設定値の正本は AppPlan.md、運用への反映は Orchestrator.md、Spec.md には混ぜない。人間の脳はフォルダの話を仕様に混ぜるとすぐ溶けるので。

## A112
結論：「/App/固定」を捨てるんじゃなくて、“Appルートを差し替え可能”にして吸収が一番マシです。
つまりあなたの案でいうと 3) だけど、実装を“重く”しない版。Unityに合わせて AppRoot = Assets/... に寄せます。

なぜか：Unityはプロジェクト直下に Assets / Packages / ProjectSettings がいて、生成物（＝ゲーム側の差分編集対象）は実質 Assets配下に閉じるのが自然。T-Hunt側の「生産物は /App/」前提は、WinFormsみたいな“非Unity”向けの整理で、Unityにそのまま押し付けるとズレて地獄になります。 

AGENTS

おすすめ構成（Unity向け “Adapter” 方式）
1) ルール上の「生産物ルート」を変数にする

T-Huntのコア思想（差分方式・運用分離・ChatRoom運用）は維持しつつ、生産物の置き場だけ差し替えます。

**Framework側（運用）**は今のまま
/THunt-Framework/...（ChatRoomやCore）

**App側（生産物）**はUnityに合わせて
/<UnityProjectRoot>/Assets/THuntApp/（ここを「AppRoot」と呼ぶ）

例：

/ (Unity project root)
  Assets/
    THuntApp/              <-- AppRoot（= ここが /App/ の代替）
      Dev/                 <-- ここに Orchestrator.md / Spec.md 等
      Runtime/             <-- Codexが触る実装（MonoBehaviour等）
      Editor/              <-- Editor拡張が要るなら
  Packages/
  ProjectSettings/
  THunt-Framework/
    Core/
    ChatRoom/


ポイント：Unityが見るのはAssets配下だけ。T-Huntの運用ファイル群はプロジェクト直下に置いてもUnity的には基本ノーダメ（Assets外なので取り込まれない）。

どうルールを変えるか（最小差分）

あなたが悩んでる「実装が複雑になる」を避けるため、“モード切替機能”をコードで作らない。
やるのは ドキュメント上の一行の定義と、編集可能範囲の解釈変更だけ。

A) AGENTS.md に “AppRoot” を導入

今のAGENTSは「生産物側＝/App/Dev」と固定してます。 

AGENTS


ここを Unity 用に例えばこう置換するのが最小：

生産物側（ゲーム・プログラムなど）

/<AppRoot>/Dev/ ...

Unityでは AppRoot = Assets/THuntApp

そして編集規則を：

各案の評価（あなたの 1/2/3）
1) Unityプロジェクトを /App/ に移す

やめとけ枠。Unityの前提（ツール、パス、CI、相対参照、Package周り）を余計に揺らして、得られるのは「T-Huntの見た目が綺麗」だけ。人間が気持ちよくなる以外のメリットが薄い。

2) /App/ 廃止（直下に作る）

これも微妙。直下に散らばると、T-Huntが作った「運用と生産物の分離」が死ぬ。あなたが後で自分を殴る未来が見える。

3) モード切替

“実装する”と重い。でも 「AppRoot変数」方式なら軽い。
モード切替というより「このリポジトリでは AppRoot はここ」って宣言するだけ。

**T-Huntのルール（差分方式・運用分離・編集範囲制限）**をそのまま持ち込める

Codexに「触っていい場所」を一発で固定できる（暴走対策として効く）

1つだけ“落とし穴”

Assets/THuntApp/Dev/ を 最小限にして、ドキュメントは Assets外（例：/AppDev/） に置く
