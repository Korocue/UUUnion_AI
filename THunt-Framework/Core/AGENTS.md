# THunt-Framework

複数のプロンプトを組み合わせたプロンプト群を利用して
大規模なプログラムを作る方式

プロンプトを利用して0からプログラムを作るのではなく
パッチ方式で差分を積み重ねていく差分方式
（最初の1回はプロンプトを使って生成をする）

初期目標はマインスイーパーのスタイルを模倣した
サンプル「宝探しゲーム」を作ること

それが達成され次第、同様の開発方式で
ゲームやプログラムを製作するフレームワークとする

## ChatGPT側のルール（重要）
レビューの際、「改善案」はなるべく簡潔に伝える
・　すべて「正常に」「完璧に」動作させる前提「ではない」
・　その上で最も重要な1点のみをユーザーに伝える

### リポジトリ仮想環境について
リポジトリファイルをChatGPTのプロジェクトファイルとして
"仮想的"に共有しています。
ChatGPT側の不具合で、プロジェクトファイルを正常に反映させる手段がありません。
更新後の正しい内容の方を「正本」として扱ってください。
**円滑な作業の大きな妨げとなるので、ファイルの2重化についての言及は厳禁です。**

## Chat.md / Pending.md / Todo.mdについて
ChatGPTと常時サポートを受けるためのファイル。
Chat.mdを通じて会話することで
ChatGPT内での誤爆も防げる上に、推敲しながら文章を書く狙い。
また、今後の進行状況で回答が変化する可能性もあるので
同じQに関して、後々質問し直して、複数のAを保持することも考慮する。

Chat.mdから有用な内容をPending.mdに隔離。
そこから本格的に実行する内容を、Todo.mdに移行して実装。

もしかしたら、Todoに移行する前にそのまま実装するかも知れないので
PendingがそのままTodo扱いになる可能性あり。

Chat層が蓄積した場合に逐次Log化する。
命名規則にChat.md内での質問番号を記載する形式にする。
（例: Log-xx.md / 無印の場合は0から）

Stage0:　Log層
Stage1:　Chat層
Stage2:　Pending層
Stage3:  Todo層

ただし初期の無印Logは初期の設計理念に関する会話があることに注意。

### Chat.mdとLog.mdの扱いについて

(1)Chat.mdについて
このファイルは作業用バッファであり、仕様・前提・判断の正本ではありません。

(2)Log.mdについて
このファイルは履歴保存用であり、現在の判断・仕様には使用しません。

特に必要がない限り、このファイルの参照は最大限避けてください。

### Chat.md内の記述ルール
Q : ChatGPTへの質問
A : ChatGPTからの返答
CQ : Codexへの質問、レビュー要求
CC : Codexへの命令案
CR(CCR) : CQに対する、ChatGPTのレビュー
CA(CCA) : CQに対する、Codexの結果表示
M : メモ（場合によってはChatGPTやCodexに投げる）
該当しない接頭辞は無視して構いません。（旧仕様です）

### コンテキスト保持に関する規則（重要）
Chat.mdは運用上Q20(2000行)程度が好ましい。
定期的にチャットクローズしてログ化する。

> 開始親Qから数えて親Qセクションが20個を超える
>> ファイル終端の`#End Of File`からの番号のついた親セクションが基準です。
>> 上記のルールに従えば`#CQ`や`#M`の可能性などもあります
> or Chat.mdが2000行を超える
> なお、開始親Qセクションの数字（xx）は「ログ化準備セクション」に記述
>> (例: # Log-xx.md / ここから開始親QセクションがQxxと判定できます)

ChatGPTは以上のような超過、肥大化を確認した場合
回答の最後に「ふぅ…。」と記述し、それとなく警告する。
（**円滑な作業のため、直接的な言及を避け**
　ロールプレイとして、サインのみを記述する）

### チャットクローズ
作業終了・コミット時などのタイミングで
逐次チャットクローズを宣言し、Chat.mdをログ化する。
その時に、ChatGPTは以下の形式で概要を生成
ユーザーにヘッダー情報を提供する。

#### ヘッダー案
以下のヘッダーはファイルパス名の下に表記される。
```
# Log-40.md
- Branch: T-Hunt-Game/b1
- Topic: WinForms bootstrap / VSCode 実行導線 / C#拡張
- Outcome: Program.cs から実行できた・コミット済み
- Keywords: vscode, csharp, launch, dotnet, winforms
```

## メインプロンプト（統合プロンプト）の基本方針 / テンプレート
オーケストレーター（統合プロンプト）として
以下のようなメインプロンプト（Orchestrator.md）を最初に起動する。
ここに載せるテンプレートは“参考例”となります。
実行時は正本となる /App/Dev/Orchestrator.md を利用してください。

```
# メインプロンプト（統合プロンプト）
あなたにはT-Huntフレームワークに従ってアプリケーションを作成してもらいます。
AppPlan.md を “何を作るか” の一次情報として扱い、差分方式で育てます。

## 入力
- 変更要求（今回やりたいこと）
- App/AppPlan.md（完成定義を含む）
- THunt-Framework/Core/Overview.md
- THunt-Framework/Core/AGENTS.md
- 既存コード（必ず先に検索して読む）

## 手順（毎回固定）
1. 変更要求を “差分タスク” に分解する
2. 適用する部品プロンプトを選ぶ（例：ウィンドウ/ボタン/ボタン処理）
3. 触るファイルを限定し、最小差分でやる（既存を尊重）
4. Codexに渡す「作業指示」を出力する（差分単位・テスト・コミット文言まで）

## 出力フォーマット（Codexへの依頼文）
- 目的：
- 選んだ部品プロンプト：
- 編集してよいパス/ファイル：
- 作業手順（差分の順番）：
- 最低限の確認（ビルド/起動など）：

## 技術スタック判定
1) まず AppPlan.md の Target を読む。
2) 次にリポジトリを見て技術スタックを推測する（Unity / Web / Python / C# など）。
3) 推測結果が Target と一致する場合のみ作業する。
4) 一致しない、または判定不能な場合は停止し、矛盾点と必要情報だけを報告する（この段階では編集しない）。
```

## AppPlan.mdの基本方針
Orchestrator.mdに基本的に渡すアプリの仕様案。
これは AppPlan.md の“例”であり、フレームワークのコア仕様ではありません。

```
# AppPlan.md（例）
## 1. ひとことで
マインスイーパー風「宝探しゲーム」（グリッド探索）

## 2. コア体験（プレイヤーが毎ターンやること）
- セルを開く
- 旗（マーク）を置く
- 数字ヒントから推理する

## 3. 勝敗条件（完成定義）
- 勝ち：条件A（例：宝を全部特定/安全セル全開）
- 負け：条件B（例：罠を踏む）

## 4. MVPスコープ（最初に作る最小）
- 盤面生成、開く、マーク、勝敗判定
- UI：開始/リスタート、難易度（後回し可）

## 5. 非目標（今回やらない）
- 演出過多、セーブ/ロード、複雑な設定画面 など
```

ポイントは「完成定義」を明文化しておくこと。
ここが曖昧だと、各プロンプトが勝手に肥大化する。

## Codexへの命令案
安全レベルに従って、下記のパターンを選択する。

### ネタ運用
レベル0: Orchestrator.md
レベル1: /App/Dev/Orchestrator.mdを実行してください

### レベル2
/App/Dev/Orchestrator.md を開いて、その指示に従って作業してください。

基本運用はこちらで問題なし

### レベル3
Dev/Orchestrator.md を読んで、要約→手順宣言→差分適用の順で実行してください。
ただし、制約や編集範囲が曖昧なら「要約」と「手順宣言」までで停止し、差分適用はしないこと。

レベル2で不安な大きめの変更時は、こちらのプロンプトを採用する

### レベル4（最大レベル）
最高レベルの完全プロンプトは、以下の形で2段階で実行します。
#### (A) プランだけ出させるプロンプト（この段階では編集させない）
リポジトリ内の App/Dev/Orchestrator.md を開いて内容を読んでください。
次に、以下の形式でだけ出力してください（このステップでは一切編集しないでください）:

1) 要約: 目的 / 制約 / 編集してよい範囲
2) 手順宣言: 変更するファイル名と変更内容を箇条書き
3) 影響範囲: 影響が出そうな箇所（UI/状態/保存など）
4) テスト: 実行すべき最小テスト

### (B) 差分適用プロンプト（プラン確定後に実行）
先ほどの「要約/手順宣言」に従い、差分を適用してください。

- 指定された範囲以外は編集しない
- 既存実装を尊重し、最小diffで変更する
- 出力は unified diff 形式（または実際にファイル更新）で
- 最後に実行したテスト結果と、変更点の短い要約を書く

## コミットメッセージ生成ルール
Codexは実行時に必ず1行のコミットメッセージを提示してください。
  - フォーマットを <type> : <section> / <message>とします。
  - <type>(<section>): <message>とするところを上記のフォーマットに成形してください。 
  -（例1: feat: new treasure button）
  -（例2: fix: tresure button / button bug）

## コードレビューと信頼性 (Codex向け)

### 目的
- ユーザーが「全体をレビューして改編案を出す」ために、コードの意図と責務をコメントで明確化する。
- 「値が何の数字か」「どの処理がどの指示に該当するか」を追いやすくしてください。

### コメント方針
- 以下を方針として簡潔にわかりやすくお願いします：
  1) この数字の意味（例：既定の行数/列数/爆弾数など）
  2) この処理の目的（例：クリックでセルを開く、勝敗判定を行う）
  3) どの仕様書に対応しているか（例：UI.md の「開始ボタン」節、GameBoard.md の「配置」節）

### どこにコメントを足すか（最小）
- ファイル先頭：このファイルの役割（何を担当しているか）
- 重要メソッドの先頭：メソッドの目的（何を保証するか）
- 変数・定数：直前に1行コメント（可能なら定数名にしてもよいが、挙動変更は禁止）
- UIイベント：どのUI要件に対応しているか

#### 例1：ファイル先頭（役割）
```
// このファイルは盤面（セル配列）の生成・状態更新・勝敗判定を担当する。
```

#### 例2：数字の意味（デフォルト値など）
```
const int DefaultRows = 10;  // 既定の縦マス数（設定ファイルが無い場合に使う）
const int DefaultCols = 10;  // 既定の横マス数（設定ファイルが無い場合に使う）
```

#### 例3：処理が「どの指示に該当するか」
```
// UI.md の「リセット」操作：盤面とスコア表示を初期化して再生成する。
private void ResetButton_Click(object sender, EventArgs e) { ... }
```

#### 例4：読み込み・保存（失敗時の挙動だけ）
```
// 設定ファイルを読み込む。無い/壊れている場合はデフォルトで続行する（起動を止めない）。
```
